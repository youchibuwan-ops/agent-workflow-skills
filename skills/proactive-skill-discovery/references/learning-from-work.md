# 从实际任务沉淀 Skill

在反复纠错、发现非显然有效方法、完成可复用工具或发现技能缺漏时使用。总结应减少未来同类错误，不以新增文件数量衡量成果，也不每个普通任务都创建 Skill。

## 从证据到可执行经验

1. **核对事实。** 找到实际触发条件、错误表现、原因、有效修正及验证产物。区分亲自观察、工具/外部模型返回和推测；无法复现的建议标为待验证，不写成已证实流程。一次失败也可能暴露重要机制，但不能仅因一次网络超时就固化重试规则。
2. **提炼决策。** 写清“何时用、怎样判断、采取什么动作、如何验证、何时不适用”。提炼导致成功的方法，不复制整段对话、临时进度或事后叙事。
3. **选择归属。** 先查已有技能：同一能力的缺漏直接修订；上游技能保留来源/许可，用适配层或许可允许的分叉承接；没有合适归属且方法能跨任务复用才新建。项目特有审美、路径和暂停点留在项目配置；凭据、私有素材和原始日志不进入共享包。
4. **完成维护。** 可用时采用宿主的 skill-creator 或等效创作流程。主体只放触发、关键决策和验证标准；较长细节放 references/，重复且确定性的操作才加 scripts/。保留现有调用策略和无关能力，避免重复技能或互相递归调用。
5. **验证实际决策。** 修改前留存原版与真实失败证据，或用现实情景检查基线；修改后用同类任务及一个相邻反例验证。检查它既能纠正目标问题，也不会把项目偏好扩散到其他任务。执行结构/引用检查，有代码则跑真实输入。基线本来正确时如实记录，不能声称测出了提升；未完成行为验证时明确验证范围，不能宣称已证明有效。
6. **记录并交付。** 简记改了哪个 Skill、来源、适用边界、验证证据和遗留限制；在授权范围内安装到可发现的个人目录。仅在已有发布授权覆盖本次变更时同步公开仓库，发布前去除私人信息并核对许可证。总结或维护 Skill 不授权发送消息、执行付费操作或恢复暂停任务。

例如：多个导出任务误看旧预览，而实际验证源修订与预览对应后有效，应补强现有导出审核 Skill 的产物对应检查；“此项目偏好绿色”仍留在项目配置。不能只保存“下次认真看”这类没有判定方法的提醒。
